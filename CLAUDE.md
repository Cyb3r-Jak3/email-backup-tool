# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
go build ./...                       # build everything
go build -o imap-backup-tool .       # build the CLI binary
go test ./...                        # run all tests
go test ./stages/transform/          # one package
go test ./stages/fetch/ -run TestIMAPHonoursTheTimeWindow -v   # one test
go vet ./...
gofmt -w cmd stages                  # main.go has CRLF endings; gofmt -l always flags it, leave it alone
go generate ./cmd/...                 # regenerate config.schema.json after changing ConfigV1
```

Running the tool needs a config file (see `config.example.yaml`, and `example.yaml` for every supported key):

```bash
./imap-backup-tool --config test.yaml login     # credential/TLS check only, downloads nothing
./imap-backup-tool --config test.yaml backup --all --attachments
./imap-backup-tool generate-key                 # age key pair (--type pgp for OpenPGP)
./imap-backup-tool decrypt -i imap-backup-key.key FILE...
```

## Architecture

A backup run is three interchangeable stages, declared as interfaces in
[stages/stages.go](stages/stages.go) and driven by [stages/pipeline.go](stages/pipeline.go):

| Stage | Interface | Implementations |
|---|---|---|
| 1 — download | `Fetcher` | `stages/fetch` (IMAP) |
| 2 — encrypt | `Transformer` | `stages/transform` (age, pgp, `PassThrough`) |
| 3 — store | `Sink` | `stages/store` (local, s3, tar, `Multi`) |

`Pipeline.Run` streams: stage 1 emits one `Message` at a time via a callback, the pipeline
flattens it into `Artifact`s (the `.eml` plus one per extracted attachment), and each passes
through stage 2 into stage 3 before the next message is fetched. A large mailbox is never held
in memory at once. Stage 3 is closed even when the run fails, so a partially written tar still
gets its trailer.

**[cmd/build_stages.go](cmd/build_stages.go) is the only place flags and config become stages.**
Every builder returns the interface, never a concrete type. Adding a mail source, encryption
scheme or storage backend means writing the implementation in its subpackage and selecting it
there — no other stage changes. `stages/*` never imports `cmd`; it takes plain option structs.

### Config resolution

Values resolve **command line > environment > YAML file**, wired by `flagSources()` in
[cmd/config.go](cmd/config.go). Flags name a *logical key* (`imap.server`, `save.s3.bucket`, …)
listed in [cmd/config_keys.go](cmd/config_keys.go); the loaded config answers it through
`VersionedConfig.Lookup`. That indirection is deliberate — a future schema version can move or
rename the underlying YAML field and satisfy the same flag without touching any flag definition.

The file is parsed once, lazily, and cached (`LoadedConfig`). A `version` key is required and
selects which struct the document decodes into; add a version by writing a `ConfigV2` that
implements `VersionedConfig` and registering it in `newVersionedConfig`. A *missing* config file
is not an error (flags and env still apply); one that exists but is malformed fails at startup
via the root `Before` hook.

[config.schema.json](config.schema.json) is a JSON Schema for the config file, generated by
reflecting over `ConfigV1`'s struct tags ([cmd/schema.go](cmd/schema.go)); `example.yaml`
references it via a `yaml-language-server` modeline so editors validate and autocomplete config
files. It is generated, not hand-maintained: run `go generate ./cmd/...`
([internal/gen-schema](internal/gen-schema)) after changing `ConfigV1`'s fields or tags, and
`cmd`'s `TestConfigSchemaUpToDate` fails the build if the committed file is stale. Field type,
name and required/optional status come straight from the struct and its yaml tags; descriptions,
enums, patterns, min/max and defaults come from the `desc`/`enum`/`pattern`/`min`/`max`/`default`
tags next to each field. A handful of cross-field constraints (`save` needing at least one
destination, `encrypt` allowing at most one key source) can't fall out of a single struct's
fields and live instead in the small `schemaOverrides` map at the top of `schema.go` — update
that by hand if such a constraint changes. Adding a `ConfigV2` needs its own schema handling if
one is ever added; `GenerateConfigSchema` only covers `ConfigV1` today.

A destination is active when its flag has a value from any source, so a `save` block listing
several backends produces a `store.Multi` that fans out to all of them.

### Encryption

Stage 2 writes **standard formats only** — age (default) and OpenPGP — so a backup stays
readable with `age -d -i KEY FILE` or `gpg -d FILE` if this tool is unavailable. That property
is the reason for the choice; don't replace it with a bespoke container.

The key material itself selects the scheme (`DetectScheme` in
[stages/transform/transform.go](stages/transform/transform.go)): `age1…` → age, an armoured
OpenPGP block → pgp. There is no separate scheme setting that could contradict the key. Stored
paths get a `.age` / `.pgp` suffix.

With no key configured the run uses `PassThrough` and warns on both stderr and the log — the
pipeline has no unencrypted special case. PEM keys from before this scheme are rejected with a
message pointing at `generate-key`; `imap-backup-key.pem` / `.pub.pem` in the repo root are
leftovers that nothing reads.

An OpenPGP key can also be fetched by fingerprint instead of read from disk/config: set
`encrypt.public_key_fingerprint` (`--public-key-fingerprint`) and optionally
`encrypt.public_key_server` (`--public-key-server`, default `keys.openpgp.org`). The lookup
([stages/transform/keyserver.go](stages/transform/keyserver.go)) speaks the HKP `op=get`
protocol and only accepts a full 40-hex-digit v4 fingerprint — no short/long key IDs, since
those aren't collision resistant. `ConfigV1.Validate` only checks the fingerprint's *shape* at
config-load time; it does not hit the network there, since `Validate` runs on every command via
the root `Before` hook and most commands never encrypt anything. The actual fetch happens once,
in `buildTransformer`, only when `backup` runs — that's the one place in stage 2 building that
needs `ctx`.

### Incremental backups

`last_message_timestamp` ([stages/watermark.go](stages/watermark.go)) is a JSON file with two
keys: `last_message_timestamp` (RFC 3339 UTC) and `version` (the email-backup-tool build that
wrote it). Precedence in `fetchRequest` ([cmd/backup.go](cmd/backup.go)): `--all` → an explicitly
passed `--duration` → the timestamp file → `--duration`'s 24h default.

The file is written **only after a fully successful run**, so a mid-run failure retries the same
window instead of skipping mail it never stored. IMAP `SINCE` compares dates only, so the
fetcher re-filters on the exact instant — a resumed run gets back messages it already has and
must drop them.

## Testing

`stages/fetch` tests run against a real in-process IMAP server
(`go-imap/v2/imapserver/imapmemserver`) on a random port, not mocks — see `startTestServer` in
[stages/fetch/imap_test.go](stages/fetch/imap_test.go). Prefer extending that over faking the
IMAP client.

`cmd` tests exercise flag precedence by building the real command and replacing its `Action`;
they must set the package-level `logger` (`logger = zap.NewNop()`), which is otherwise nil
outside `BuildApp`.

Encryption changes need a genuine round trip *and* a format check — a self-contained round trip
passes happily on a key that real `gpg` rejects. This has already bitten once:
`SerializePrivateWithoutSigning` produced an OpenPGP key GnuPG refused to import, because a
freshly generated entity has no self-signatures yet. Use `SerializePrivate`, and call it before
`Entity.Serialize` or the public half is written without them too.

### End-to-end suite

[e2e/](e2e/) drives the real CLI (`cmd.BuildApp`, main.go's own entry point) against real backing
services from [e2e/docker-compose.yml](e2e/docker-compose.yml): GreenMail as the IMAP+SMTP server
and RustFS (an S3-compatible store) as the bucket. It is opt-in via a build tag, since it needs
Docker and takes longer than the rest of the suite:

```bash
go test -tags e2e ./e2e/...
```

`TestMain` brings the compose stack up once per run and tears it down after; individual tests each
create their own bucket so they don't have to reconcile objects against each other, even though
they share one IMAP mailbox. Test mail is seeded over real SMTP (`net/smtp`), not IMAP `APPEND`:
empirically, a second command issued on a connection that just did an `APPEND` against GreenMail is
unreliable with the beta `go-imap/v2` client this project uses, while the fetch path itself
(`stages/fetch`'s `Login`/`List`/`Select`/`Fetch` sequence) has shown no such issue. If a future
change needs APPEND-based seeding, verify it against a live GreenMail container first rather than
assuming the client's over-the-wire behavior matches its in-process test-server behavior.

## Gotchas

- Backups select mailboxes read-only and fetch with `Peek`, so a run never sets the seen flag on
  the user's mail. Keep it that way.
- The S3 sink has no test coverage against a live service; only its construction is exercised.
